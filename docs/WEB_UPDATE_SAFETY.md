# 页面更新与正在编辑的画布

## 开发与构建

- `npm.cmd run dev` 使用开发服务器。
- `npm.cmd run build:check` 包含 TypeScript 检查及临时目录生产构建，完成后仅清理本次临时产物，不改当前 `dist`。
- `npm.cmd run build` 先在临时目录完成生产构建，成功后将完整静态资源放到 `dist`，最后通过文件重命名切换 `index.html`。同名哈希资源内容冲突或入口资源不完整时拒绝切换。发布锁阻止同时写入；进程意外退出留下 `dist/.web-publish.lock` 时，应确认没有发布进程后由维护者处理，不自动抢锁。
- 不在用户使用期间直接运行原始 `vite build` 覆盖服务目录，也不删除旧 `assets`。保留旧哈希资源用于旧页面的延迟加载，不是用户项目备份；它们会增加磁盘占用，当前不自动清理。维护清理应安排在所有旧页面关闭之后。第三方直接覆盖/删除整个安装目录不受该机制保护。
- 前端资源缺失返回不缓存的 404，不能被误判为 Bridge 权限错误。HTML 本身继续使用 `no-store`，哈希资源继续使用 immutable 缓存。

## 用户体验与数据保护

- 可选弹窗／侧栏各自隔离加载失败，只显示局部重试提示，画布不因此卸载；详细错误默认折叠。重试重建 React.lazy 实例，不复用已拒绝的加载 Promise。
- 新版本依据当前与服务器 HTML 的模块入口地址判断，不能仅凭网络失败宣称更新。前台每分钟及窗口重新聚焦时检查；开发模式不执行。即使发现更新也不自动刷新。
- 用户主动点击“保存并更新”后，文本节点和单节点指令框先提交本地草稿（包括参考项与参数），再等待 Bridge 保存。未完成弹窗、设置、AI 聊天、生成任务和无法归属单节点的多选草稿不应被刷新丢弃。
- 保存失败、六秒内无法确认完成、保存期间内容变化均停止刷新；短暂阻挡新输入只发生在用户主动发起保存更新之后。此流程不绕过既有持久化冲突校验。
- 本机制只能保护加载了新代码的页面。首次升级前已打开的旧页面仍需要在确认保存后刷新一次；此前已删除的旧资源不会凭空恢复。

## 验证入口

- `web-build-publication.test.mjs`：保留旧动态模块、完整入口校验、哈希碰撞不切换。
- `local-bridge-pairing.test.mjs`：缺失静态资源 404 与 Bridge 权限隔离。
- `src/lib/webBuildUpdate.test.ts`：版本识别、离线/错误页面不误报。
- `src/lib/pageUpdateDrafts.test.ts`：草稿提交、编辑门禁、保存失败/超时/竞态。
- 浏览器验收应覆盖“保持旧页面 → 新构建 → 首次打开延迟模块”，以及局部失败后的持续输入、重试、主动更新与保存失败不刷新。
